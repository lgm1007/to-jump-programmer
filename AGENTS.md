This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

## Project notes (To Jump Programmer)

- Learning content: the full set lives in a **private** repo (`../to-jump-content`, override with `TJ_CONTENT_DIR`); this public repo only ships `src/content/sample/`. `npm run content:sync` copies full content (or the sample when the private repo is absent) into `src/content/data/` (gitignored, but uploaded to EAS via `.easignore`; keep `.easignore` in sync with `.gitignore`). Never commit full content to this repo. Schema: `src/content/types.ts`, writing rules: `docs/CONTENT_GUIDE.md`. After editing content run `npm run content:sync && npm run validate` (algorithm patterns: every implementation is executed in all 5 languages against the example tests; Spring's Kotlin review code lives in `review/spring-kotlin.ts` variants keyed by pattern/challenge id); refresh the sample with `npm run content:sample`.
- `production` EAS builds fail unless `src/content/data` holds the full content (`eas-build-post-install` → `content-sync.mjs --eas`).
- Algorithm learning is read-only: topic primer (`algorithm/quiz/<topic>.ts`) → patterns (`algorithm/patterns/<id>.ts`, one `AlgoPattern` per file, index generated by `scripts/gen-content-index.mjs`) → 1–3 implementations × 5 languages with key points whose `lines` are set **per language** (check with `npx tsx scripts/show-pattern.ts <id> --lines`). The app never runs user code — the old solve/run/grade feature (Pyodide, Piston, CodeMirror editor) was removed in #9; keep the persisted `problems` records (old users' history) but don't build UI on them. Example code is verified only at authoring time by `scripts/validate-content.ts`, which uses the Java/Kotlin/C++ harness generators in `scripts/lib/harness` (keep that harness within Kotlin 1.8 / JDK 8 syntax so content can be checked against old coding-test compilers via `KOTLINC`/`KOTLIN_JAVA_HOME`).
- Developer course: `profile.track` is `backend | frontend | fullstack`; `framework` is the backend framework and `frontendFramework` the frontend one (fullstack uses both). Course scoping lives in the pure module `src/features/progress/course.ts` (CS categories carry `track`/`framework`, review frameworks carry `track`) and drives the daily plan, the interview tab ordering (`partitionCategoriesForCourse`), the review tab (fullstack gets a backend/frontend toggle) and track summaries — add new filters there, not in screens. The daily quiz scope is `isQuestionForCourse`/`questionScope`: CS questions from `csCategoriesForCourse` only, algorithm questions only when they have no code or their `code.language` is one of the user's languages (coding-test language + chosen frameworks' languages); saved daily plans are re-checked against that scope (`quizUpToDate`). Persisted progress is versioned (`PROGRESS_VERSION` + `migrateProgress` in `progress/migrate.ts`); bump the version and add a migration step whenever a persisted field needs a default for old users.
- CS theory lessons: each CS category file is `{ lessons, quiz, cards }`; quiz questions link to a lesson with `lessonId` (every lesson needs ≥3 linked questions — `validate` enforces it). Lesson screen `/interview/lesson/[id]`, check quiz = `/quiz?mode=lesson&id=…` (3 questions, unseen first, submitting marks the lesson done; ≥2/3 correct shows "이해함"), quiz explanations push the linked lesson with `from=quiz` so the quiz session stays on the stack. Lesson state/selection helpers are pure (`progress/lessons.ts`).
- Multiple choice: MCQs are either `choices`+`answer` (legacy, order shuffled) or a pool `correct`+`distractors[{text, why}]` (+`pick`, default 3). Screens never read `choices`/`answer` directly — use `presentMcq(q, attempt)` / `correctChoiceText` from the pure `progress/choices.ts` (deterministic per question id + attempt count, so the layout is stable while viewing and changes on the next attempt); review challenge options use `shuffledOrder` and are graded by original index. Explanations must not point at choices by position (A번, **B**, 두 번째 선택지) — `validate` errors on it.
- Ads: Google AdMob via `react-native-google-mobile-ads` in `src/features/ads/` (`index.tsx` native, `index.web.tsx` no-op). The library is `require`d lazily so Expo Go (no native module) still runs without ads — never import `react-native-google-mobile-ads` outside `ads/google.tsx`. AdMob IDs come from `ADMOB_*` env vars read in `app.config.ts` (test IDs when unset; `__DEV__` always uses test units). Interstitial frequency: `INTERSTITIAL_POLICY` in `ads/config.ts`.
- Web (PWA): `npm run build:web` (`scripts/build-web.mjs`: expo export → PWA head tags, manifest, Workbox `sw.js`, per-route pages + `sitemap.xml` via `scripts/web-routes.ts`) and `npm run preview:web`. Every content route gets its own `index.html` with title/description/canonical and the real content pre-rendered as HTML inside `#root` (`scripts/lib/prerender.ts` — keep it in sync when adding content screens; only put content that the app screen also shows); React's `createRoot` clears `#root` when the app boots. App-function screens (onboarding/quiz/cards/settings/bookmarks/notes/me) get empty `noindex` pages. The service worker answers navigations with the empty `app-shell.html`; unknown paths get `404.html` (`not_found_handling: 404-page`). On web, first-time visitors are not redirected to onboarding (guests browse with the default profile; native still redirects). The AdSense script is never in the page `<head>` — `AdSlot` (web) injects it on first mount, so screens without publisher content never request ads; don't add `AdSlot` to result/completion or other non-content screens. Deployed to Cloudflare Workers static assets (`wrangler.jsonc`, SPA not-found handling, custom domain https://jumpprogrammer.app at the site root) by `.github/workflows/deploy-web.yml` (pulls the private content with the `CONTENT_DEPLOY_KEY` secret; Cloudflare secrets `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`). The build also writes root `robots.txt`/`ads.txt`/`app-ads.txt`. `TJ_WEB_BASE_URL` (sub-path deploys only) sets `experiments.baseUrl` in `app.config.ts` — never hard-code it. Details: `docs/WEB.md`.
- Web-only modules use `.web.ts(x)` siblings with a native stub of the same API: `features/ads/index.web.tsx` (AdSense; `AdSlot` goes between content sections, never next to the tab bar or footer buttons — AdSense accidental-click policy), `features/pwa/install.web.ts`, `features/progress/backup-file.web.ts`. No ads on screens where the user is solving (quiz in progress, card session).
- `plugins/with-ios-scene-lifecycle.js` adds the UIScene life cycle (SceneDelegate → `ExpoAppSceneDelegate`) that the iOS 27 SDK requires; the SDK 57 template lacks it. It no-ops once the template already has it (SDK 58+), so remove it after upgrading.
- On iOS the native `SafeAreaView` reports zero insets on the first `fullScreenModal` presentation after launch (quiz/cards overlapped the status bar). Full-screen modals and `Footer` use `InsetView` (`components/ui/screen.tsx`, insets from the root provider) — don't switch them back to `SafeAreaView`.
- Local iOS builds fail with a codesign "detritus" error while the project sits in an iCloud-synced folder (`~/Documents`, `~/Desktop`); build from a non-synced copy/location.
- Before finishing: `npm run typecheck`, `npm run lint`, `npm test`.
